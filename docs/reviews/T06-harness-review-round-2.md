## Part B — fresh findings, ordered by severity

1. High — a completed evaluation run can have no report. run-and-score completes its run before calling score_all (main.py (harness/__main__.py:43)). The scorer checks every run already in the output folder before writing any report (score.py (harness/score.py:343), score.py (harness/score.py:348), score.py (harness/score.py:386)). I reproduced this using temporary output: after corrupting an older run’s items.jsonl, a second run-and-score returned 1, while its new manifest said completed and its report.json did not exist. The existing changed-items test establishes the all-or-nothing scorer refusal (test_score.py (tests/t06_harness/test_score.py:441)), but does not exercise a later evaluation run. This leaves AC-24 and the evaluation-run claim in DEC-T06-MANIFEST-3 unmet in that case.
2. Medium — the mutation classifier can report a false catch. run_guards sets out_of_memory for any nonzero exit whose output contains MemoryError (mutations.py (tests/t06_harness/mutations.py:215)). An in-memory probe returning exit -15 with stdout MemoryError produced (-15, [], True); prove then labels that broken copy “out of memory” (mutations.py (tests/t06_harness/mutations.py:275)). That contradicts the active decision that a copy ended by a signal is never a catch (project.json (.genesis/project.json:1106)). The current signal test uses an output without that text.
3. Low — one active decision is inconsistent with the new cost figure. DEC-T06-TWINS says twins are outside every cost-per-alert figure (project.json (.genesis/project.json:857)). DEC-T06-COST-3 and the code deliberately include twins in the second per-item cost figure (project.json (.genesis/project.json:1093), score.py (harness/score.py:210)). The second figure is useful and matches the literal wording of SPEC.md (SPEC.md:136); the older active record needs correction.
4. Low — the design still makes broader status claims than the code. Its introduction says it writes a report “for every run,” while its own workflow and the CLI say bare run writes none (harness-design.md (docs/harness-design.md:14), harness-design.md (docs/harness-design.md:106)). The future-tense testing claim noted in Part A is also stale.

The remaining active decisions are supported by the code and tests I inspected, within their stated fixture and sample limits. The scoring populations and calculations for SPEC.md:126–138 are supported by the micro-world and independently counted full-world tests (test_score.py (tests/t06_harness/test_score.py:167), test_cost.py (tests/t06_harness/test_cost.py:231)). The all-items cost is present as a second figure; the headline remains main-only, as the accepted decision states. I found no shared output fixture edited in place: shared folders are digested, and tests that alter run data copy the folder first (conftest.py (tests/t06_harness/conftest.py:42), test_sets.py (tests/t06_harness/test_sets.py:81)).
