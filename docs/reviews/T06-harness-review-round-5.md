## Part B — fresh review, grouped by problem class

1. CONTRADICTS an active record or a SPEC requirement — the new report is not written before older runs are touched. DEC-T06-MANIFEST-5 (.genesis/project.json:1162) promises that order. score_all reads the shared index and loads all runs at score.py (harness/score.py:383)–score.py (harness/score.py:400); only afterward does it write the first report at score.py (harness/score.py:463). A temporary-folder read/write probe observed load new → load old → write new. Thus a stalled older manifest or items read can still delay the new report. The existing test checks the order listed in the set report, not this I/O order.
2. CONTRADICTS an active record or a SPEC requirement — cross-file run identity, validity and table data are trusted without validation. These instances share the same missing boundary check:
   - The scorer does not reconcile the index’s run_id, run_set and state with the manifest’s values, or verify run_set_inputs against the set ID. It groups by the index set at score.py (harness/score.py:412), although an active decision defines a set by ten shared inputs at project.json (.genesis/project.json:921).
   - _check_fields merely accesses git.dirty and infra_invalid.marked; it does not require booleans at score.py (harness/score.py:336). In a temporary copy, setting both to numeric 0 caused no exclusion and left a three-run set eligible as a baseline.
   - The score step does not rerun the price and time schema checks used at run creation (run.py (harness/run.py:138)), or recheck either embedded table hash. Invalid kind values in both tables were accepted and made the run report say mechanism_only: false, contrary to the fixture-label decisions at project.json (.genesis/project.json:1082) and project.json (.genesis/project.json:1095).
   - A changed older price remained in its original set with no exclusion. Its per-run cost used the changed table, while the pooled cost used the set’s last table at score.py (harness/score.py:473) and score.py (harness/score.py:508). The set remained eligible.

   These cases violate the wrong-type quarantine and baseline eligibility promises in DEC-T06-MANIFEST-5 (.genesis/project.json:1164). The round-4 tests exercise types that raise during calculation; they do not catch types that Python silently treats as valid.
3. CONTRADICTS an active record or a SPEC requirement — rehashed item data can silently change a completed run’s figures. The loader verifies bytes against the manifest hash, then parses and sorts rows at score.py (harness/score.py:324); it does not check row count and uniqueness or reconcile item_id, alert_id, framing and twin with the manifest and world. Figure paths also use sent_ids, cited_ids, system_failure, citation_invalid, failure_kind, latencies and attempts without a row schema check (score.py (harness/score.py:78), score.py (harness/score.py:82), score.py (harness/score.py:194)). Some malformed values raise and are quarantined; others silently change results. In a temporary copy, one rehashed row with twin: "false" produced 1,799 main and 46 twin items, while its manifest still said 1,800 and 45. It was not excluded, and its three-run set remained baseline-eligible. This contradicts FR-20 and AC-24 (SPEC.md:34) and the active wrong-type quarantine rule.
