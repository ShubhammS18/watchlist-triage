## Part B — fresh findings

1. High — AC-24 can still fail after an older run is damaged. Per-run exclusion catches only ScoreRefused (score.py (harness/score.py:352)). A completed older manifest with a missing outputs field raises KeyError at score.py (harness/score.py:320). I reproduced KeyError: 'outputs' with an older manifest containing {"state":"completed"} and an items file. The exception stops the loop before reports are written (score.py (harness/score.py:398)); the CLI does not catch KeyError (main.py (harness/__main__.py:68)). The new hash-mismatch test covers one kind of damage, not this one. This contradicts the scorer’s per-run refusal claim and leaves the active evaluation-run commitment in DEC-T06-MANIFEST-3 unmet for this case (project.json (.genesis/project.json:1055)).
2. Medium — the timed-run gate can proceed without a confirmed charger or successful benchmark. power_check.sh prints unknown for an unreadable path (power_check.sh (tools/power_check.sh:6)), but timed_run.sh refuses only the exact ON BATTERY message (timed_run.sh (tools/timed_run.sh:11)). I ran it with a missing power path and a dummy benchmark: it printed Power: unknown and executed /bin/true. The wrapper also parses benchmark output without checking the benchmark’s exit code or its stated N and result (timed_run.sh (tools/timed_run.sh:18)). The tests cover battery and a slow formatted output, but not these failures (test_timing_tools.py (tests/t06_harness/test_timing_tools.py:96)).
3. Low — the memory guard’s kill trigger is system-wide. It reads the machine’s Mem: used value and kills the guarded process group when that value crosses the limit (memory_guard.sh (tools/memory_guard.sh:7), memory_guard.sh (tools/memory_guard.sh:18)). Memory used by an unrelated process can therefore kill a healthy guarded command. setsid normally confines the signal to the command’s own group, so I found no ordinary path that directly kills an unrelated process group. The kill test makes the guarded child allocate memory; it does not test an unrelated memory spike (test_timing_tools.py (tests/t06_harness/test_timing_tools.py:40)).
4. Low — several descriptions still overstate or misstate the code. The design glossary says twins feed “the injection measure and nothing else” and that every cost figure uses main items (harness-design.md (docs/harness-design.md:61)); the all-items cost figure includes twins. Its index table lists infrastructure-invalid as a run state (harness-design.md (docs/harness-design.md:129)), while the code keeps state completed and records a separate mark (run.py (harness/run.py:347)). The scorer module header likewise says twins feed injection figures only (score.py (harness/score.py:8)). These do not change the computed figures, but they can mislead a reader of the report format.

Apart from the malformed-run failure against DEC-T06-MANIFEST-3, I found the active decisions consistent with the implementation at the scope tested: the main and all-items cost populations, fixture labels, modelled-time breakdowns, reference agents, and sample child path have targeted checks. The full-world cost and time tests derive expected counts from the fake model’s rule (test_cost.py (tests/t06_harness/test_cost.py:258), test_cost.py (tests/t06_harness/test_cost.py:429)); they do not establish real-provider prices or review times. I ran the full benchmark separately; it printed result 983797.
