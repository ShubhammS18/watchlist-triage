# W2-08 release protocol — round 1 design review

Scope: `docs/w2-08-release-protocol.md`, checked against the W2-08 outcome and the four named decisions in `.genesis/project.json`. I read `harness/release_check.py` to trace its current input order. No implementation or gate run exists yet. The four seed vectors in the design match the stated SHA-256 function.

## Findings

1. **BLOCKER — Early refusal suppresses required safety counts** (`docs/w2-08-release-protocol.md:88-90, 131-139, 154-178`). The design says a failed step stops before later inputs are read. Thus six runs, five runs with only two valid, a missing checkpoint, or an invalid run set stop at step 3 before step 4 counts unsafe answers. `DEC-W2-RELEASE-RULES`, `DEC-W2-08-CHOICES`, and the W2-08 outcome require unsafe answers from every run with output to count, including replaced runs. A published NOT ELIGIBLE result could hide a recorded unsafe close. **Fix:** Separate structural eligibility from safety accounting: after the world anchor is established, collect and report safety counts from every readable run even if a run or set is ineligible; mark untrusted or unreadable runs explicitly. Stop early only where reading later data would use an untrusted world. Add tests for cap and checkpoint failures that also contain an unsafe answer.

2. **BLOCKER — Unfinished logs have no specified integrity or identity check** (`docs/w2-08-release-protocol.md:161-183, 324-328`). Step 4 counts complete records of a never-finished log “as they stand,” with no checkpoint. It does not say to validate each record's schema, canonical form, sequence, hash chain, run ID, or `run_started` world, commit, and run set against the index and freeze. A truncated or fabricated log could be accepted as zero unsafe answers, while the index still consumes only one of five runs. The admitted possibility of losing tail records does not justify accepting malformed or mismatched records that *are* present. **Fix:** Define a prefix validator for uncheckpointed logs, bind its `run_started` fields to the indexed run and regenerated/frozen world, count only validated recommendation records, and make malformed or mismatched available records NOT ELIGIBLE. Keep the explicit “unverified: no checkpoint” label and the disclosed undetectable-tail limit.

3. **SHOULD — The committed generation record is not fully specified as checked** (`docs/w2-08-release-protocol.md:56-79, 277-283`). Replay is specified for counters, seeds, outcomes, and the accepted world hash, but the design does not require comparing a rejected try's `error_type` and `error_sha256` with the replay, or validating `generator_version`, `python`, record version, exact fields, and the ten-rejection shape when `accepted` is null. The record can therefore claim a different rejection or an all-rejected result with fewer than ten tries while the prose says the check never trusts it. **Fix:** Define a strict record schema and compare every recorded field with independently computed replay data; require counters 0 through 9 and ten verified `BuildError` rejections for `accepted: null`. Test wrong rejection hash and shortened all-rejected records.

4. **SHOULD — Index-only run inventory can omit a copied run** (`docs/w2-08-release-protocol.md:106-115, 131-139, 245-247, 326-328`). “Every index entry counts” does not establish that every `release/<world>/<run_id>/` directory is indexed. A copied killed run with a log but no checkpoint can be left out of `index.json`, evading both the five-run cap and unsafe-answer count. The stated limit covers runs omitted from *both* output and checkpoints, but a present unindexed folder is detectable. **Fix:** Require an exact match between run directories and index run IDs, and check `SHA256SUMS`/set-file inventory for unlisted output. Make orphan output NOT ELIGIBLE and include its available safety records in the report.

5. **SHOULD — End-point diff does not prove the after-freeze rule** (`docs/w2-08-release-protocol.md:94-104, 284-290`). `git diff --name-status --no-renames FREEZE HEAD` sees only the final tree. An intervening commit can change a frozen prompt, configuration, target, or code file and later restore it, yet pass this check. The design argues freeze-commit run manifests make that safe for counted runs, but the records separately require that nothing pinned by the freeze changed after it. **Fix:** Inspect the file changes of each commit from freeze through publish, or narrow the stated guarantee explicitly to final-tree equality and show why that satisfies the owner rule. Test a change-and-revert history.

6. **SHOULD — Qualified pass sign-off is not checked on the actual release** (`docs/w2-08-release-protocol.md:189-191, 248-250, 257-268`). The owner sign-off is required by `DEC-W2-RELEASE-RULES` and `DEC-W2-08-CHOICES`, but the check does not parse the release log and the proposed gate exercises only made-up sign-off rows. A publish commit can contain a qualified PASS with no Console sign-off and still have its check output reproduced. **Fix:** Have the publish gate parse the committed release log for the real qualified result and matching owner sign-off, using the specified row rule. A missing sign-off should make the published result inconsistent or NOT ELIGIBLE.

7. **SHOULD — Finished-run log and items are only linked by a file hash** (`docs/w2-08-release-protocol.md:154-160, 172-183, 300-303`). `audit.verify` checks a log against its checkpoint, and `run_ended` can name the items file's hash. Neither condition says that each log recommendation agrees with the corresponding scored items row. A completed run can therefore score one set of answers from items while its publicly anchored log describes another, contradicting the claim that every finished recommendation is anchored there. **Fix:** Compare the checked recommendation records with the checked items, including item IDs, verdict, system-failure flag, citations/outside-bundle count, and coverage, before accepting a completed run. Test a mismatched recommendation with otherwise valid hashes.

8. **SHOULD — Freeze-tag publication order is an owner claim, not a checked fact** (`docs/w2-08-release-protocol.md:229-235, 315-320`). The choices record requires tagging and pushing the freeze before making the fresh world. The steps instruct this, but the proposed gate uses local test commits and the release check sees only the eventual repository state; neither can establish when a remote tag became public relative to generation. The limits section discloses private commit shopping, but not this specific uncheckable ordering. **Fix:** State explicitly that the ordering needs an external, dated remote observation or owner attestation, and include that evidence in the release log. Do not claim the local gate proves the push-before-generation rule.

## Coverage and limits

The design otherwise carries the documented 0–9 seed function, freeze-generator replay, two world-specific judgments, exactly three valid runs within five indexed runs per world, replacement rules, checkpoint requirement for completed/aborted runs, and byte-identical non-release path. The four seed vectors were independently recomputed. This round is design-only; no code or gates were run. The design correctly discloses that private freeze-commit shopping, runs omitted from all committed evidence, and missing tails of uncheckpointed logs cannot be proved away from the published artifacts.
