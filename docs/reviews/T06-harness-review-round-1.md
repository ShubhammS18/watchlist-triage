# T06 harness review — DO NOT APPROVE

The scoring and run paths have substantial test coverage, but I cannot confirm that T06 meets every requirement assigned to it. I found two requirements gaps and a mutation proof that can report a false catch. This was a read-only review; I did not run the test gate or change files.

## Findings, ordered by severity

1. FR-20’s required breakdown is incomplete. FR-20 requires every Metrics figure by run, framing, and primary family (SPEC.md (SPEC.md:34)). The scoring code puts cost in one main/twin/total block and modelled time in run/framing cells; neither has a primary-family breakdown, and cost has no framing breakdown (score.py (harness/score.py:183)). The family cells cover the other figures (score.py (harness/score.py:206)). The AC-24 test checks that cost and modelled time exist, but does not test those missing breakdowns (test_cost.py (tests/t06_harness/test_cost.py:396)).
2. AC-24 is not met by a completed run command alone. AC-24 says every evaluation run produces a report (SPEC.md (SPEC.md:97)). run() writes items and a manifest, then returns (run.py (harness/run.py:342), run.py (harness/run.py:376)); the CLI requires a separate score command to create reports (main.py (harness/__main__.py:37)). A test explicitly expects the run output to contain only the index, manifest, and items file (test_manifest.py (tests/t06_harness/test_manifest.py:74)). If “evaluation run” means a mandatory run-then-score workflow, that workflow needs to be made explicit and checked. As built, a successful run can have no report.
3. The mutation gate can accept the wrong failure. Any negative subprocess exit code is classified as “out of memory,” including signals unrelated to memory exhaustion (mutations.py (tests/t06_harness/mutations.py:203)). That classification bypasses the named guard and failure-reason check (mutations.py (tests/t06_harness/mutations.py:259)). An untouched copy can also be marked “passed” with exit code 1 when its failure is unrelated to the named guard (mutations.py (tests/t06_harness/mutations.py:260)). Both conflict with the active mutation-proof decision’s requirement that unexpected endings are not catches (project.json (.genesis/project.json:998)). The negative test covers an unexpected named failure reason, not these two cases (test_mutation.py (tests/t06_harness/test_mutation.py:39)).
4. AC-25 remains unconfirmed. It requires repository history showing that modelled-time parameters were committed before the first baseline run (SPEC.md (SPEC.md:98)). The T06 design explicitly assigns that commit and run to T07 (harness-design.md (docs/harness-design.md:41), PLAN.md (.genesis/PLAN.md:59)). The parameter file inspected here is a test fixture; I found no baseline-run commit in the history reviewed. I cannot confirm this requirement at T06.
5. The cost population needs a specification decision. SPEC defines cost per alert as total model cost of a run divided by its alert-framing items (SPEC.md (SPEC.md:126), SPEC.md (SPEC.md:136)). The implementation divides main-only cost by 1,800 main items, while separately reporting twin and total cost (score.py (harness/score.py:186)). The active decision deliberately chooses that interpretation (project.json (.genesis/project.json:959)); the run nevertheless processes 45 twin items as separate calls (run.py (harness/run.py:167)). I cannot confirm that the main-only headline matches the literal “total model cost of a run” definition without clarifying whether twin items are excluded from that denominator.
6. The design document has a stale status claim. Its opening says no harness code or tests exist (harness-design.md (docs/harness-design.md:3)), although both are present. This does not change scoring, but makes the document inaccurate as built.

## What the review supports

The core Metrics calculations use the specified main-item populations for missed true matches, ambiguous closes, over-escalation including failures, citation measures, verdict consistency, injection pairs, latency, and modelled review time (score.py (harness/score.py:70), score.py (harness/score.py:107), score.py (harness/score.py:143), cost.py (harness/cost.py:149)). The micro-world tests use literal expected counts, and the full-world tests count expected results separately (test_score.py (tests/t06_harness/test_score.py:43), test_score.py (tests/t06_harness/test_score.py:167)). These support FR-22, FR-24, NFR-1, NFR-3, NFR-6, and AC-7, with the fixture-only and future-target limits stated in the design. The reference-agent acceptance checks have direct tests (test_reference.py (tests/t06_harness/test_reference.py:99)).

Failure scoring uses system_failure to force ESCALATE even if a result says CLOSE (score.py (harness/score.py:70)), with a contrary-CLOSE test (test_score.py (tests/t06_harness/test_score.py:121)). Agent exceptions and invalid log hand-overs abort a run (run.py (harness/run.py:177), run.py (harness/run.py:322)); dirty and infrastructure-invalid completed runs remain reported but are excluded from the valid three and their spread (score.py (harness/score.py:339), test_sets.py (tests/t06_harness/test_sets.py:107)). I found no shared output fixture that a test edits in place: shared folders are digested and mutation tests work on copies (conftest.py (tests/t06_harness/conftest.py:42), test_sets.py (tests/t06_harness/test_sets.py:81)).

The run path selects non-hidden world files and does not import worldgen.truth; scoring imports truth only after loading and checking run outputs (run.py (harness/run.py:154), score.py (harness/score.py:318)). Tests probe a whole run with no hidden folder and use a child file-access recorder on a 36-item sample, including a positive control (test_run.py (tests/t06_harness/test_run.py:351), test_child.py (tests/t06_harness/test_child.py:55)). That supports the sample-tested child claim. I cannot confirm this as a guarantee for every child call or a real provider; the design itself limits the claim to the sample (harness-design.md (docs/harness-design.md:554)).

I reviewed all 29 DEC-T06 records as 19 active decisions and 10 superseded historical records. Apart from the mutation-proof conflict above and the cost interpretation requiring clarification, I found no further direct contradiction in the active decisions. I independently read the saved rehearsal outputs: each of its three 1,845-item child runs matched the saved in-process output after timing fields were removed. I did not independently rerun the gate, verify the reported power-mode timing, or establish the absence of child processes at the earlier rehearsal time.
