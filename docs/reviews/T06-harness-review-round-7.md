## Part B — remaining instances by problem class

B1. Refused-run eligibility and index range — CONTRADICTS an active record or a SPEC requirement. These are the two ways a refused fourth run can be assigned away from the set whose three other runs remain eligible:

- Invalid index state. If the index says bogus while the manifest says completed, validation refuses the run, but grouping retains the index state. The refused_runs filter looks only for index state completed, so it omits this refusal and can mark the three-run set eligible. The path is visible in score.py (harness/score.py:618), score.py (harness/score.py:639), and score.py (harness/score.py:692). I confirmed the resulting eligible_as_baseline: true and empty refused_runs with an in-memory _set_report probe. This violates the fail-closed rule in DEC-T06-MANIFEST-7 (.genesis/project.json:1204).
- Invalid index run_set. A completed run whose index has a non-hash run-set ID is refused for disagreeing with its manifest, but score.py (harness/score.py:618) groups that refusal under the index’s invalid ID. Its actual set can therefore retain three valid runs and be marked eligible by score.py (harness/score.py:701). The run-set ID is specified as the hash of the inputs in score.py (harness/score.py:505); its index-side shape is not checked before grouping. This is a single index-field alteration and requires no hash rewrite.

B2. Scored result enum — CONTRADICTS an active record or a SPEC requirement. result.failure_kind accepts any string or null in score.py (harness/score.py:431), though the agent’s allowed kinds are enumerated in recommend.py (baseline_agent/recommend.py:20). An unknown string passes validate_run; a failed item then increments failures but appears in no failures_by_kind cell, which iterates only known kinds in score.py (harness/score.py:130). An in-memory figure probe produced four failures but only three classified failures. The active fault record requires high-failure runs to be published with their breakdown by kind: DEC-T06-FAULTS-2 (.genesis/project.json:1206) is not that record; its applicable requirement is stated in harness-design.md (docs/harness-design.md:176).

B3. Recorded manifest shapes outside the row schema — CONTRADICTS an active record or a SPEC requirement. The completed-run schema checks calls and cost only as objects, while duplicated index values are compared only for equality: score.py (harness/score.py:420) and score.py (harness/score.py:441). Thus matching malformed values in the index and manifest pass. The unchecked numeric instances are calls.attempts, calls.without_token_counts, calls.input_tokens, calls.output_tokens; and the counts and amount fields under cost (known_cost.numerator, known_cost.denominator, attempts, attempts_without_token_counts, attempts_without_price, at_least, and rounded). I confirmed that matching calls.attempts: -1 and a wrong-type cost statement pass validate_run in memory. Aborted-run calls and cost are then published directly from the index in score.py (harness/score.py:623), contrary to the recorded calls and known-cost requirement in harness-design.md (docs/harness-design.md:135).

The same published-manifest gap covers these additional, individually unchecked field groups from the manifest written in run.py (harness/run.py:347): git.commit; infra_invalid.transient_share; timing.duration_s and timing.queue_s; ended_at and the format of started_at; outputs.items_file; agent; world.generator_version and world.rubric_version; model.used, model.provider, model.requested, and the counts in model.reported; prompt; decoding; retry_policy; review_policies; config_sha256; framing_code_sha256; python_version; workers; and pacer_per_minute. Missing groups or values of the wrong type pass the completed-run schema and are copied into the report at score.py (harness/score.py:674). Several are expressly required manifest contents under NFR-3 (SPEC.md:44) and DEC-T06-MANIFEST-7 (.genesis/project.json:1206). I confirmed representative wrong-type git.commit, transient_share, and timing values in memory; the rest follow from their absence from SCHEMA (harness/score.py:394). Fields inside run_set_inputs are protected by its content hash and are excluded from this finding.

B4. Non-completed manifest boundary — CONTRADICTS an active record or a SPEC requirement. For a run treated as non-completed, validate_run returns before the manifest schema in score.py (harness/score.py:501). Its aborted record is not shape-checked: a list passes if the index cause is null, because only dictionary abort records contribute a cause. I confirmed that case in memory. The index’s aborted calls and cost are likewise published without a numeric check in score.py (harness/score.py:623). The active fault policy requires aborted attempts and their known cost to remain recorded and reported; see harness-design.md (docs/harness-design.md:135).
