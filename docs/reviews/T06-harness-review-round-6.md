## Part B — remaining findings by problem class

1. Baseline validity — CONTRADICTS an active record or a SPEC requirement. These are the remaining instances of the same boundary gap:
   - The index’s dirty flag is not compared with manifest.git.dirty; only run ID, set and state are compared. Scoring trusts the manifest flag when deciding whether to count the run. A manifest saying false and an index saying true passes validate_run. This conflicts with the dirty-run exclusion in DEC-T06-MANIFEST-6 (.genesis/project.json:1179). Evidence: score.py (harness/score.py:386), score.py (harness/score.py:395), score.py (harness/score.py:540).
   - The index’s infra_invalid flag is likewise not compared with manifest.infra_invalid.marked. Nor is marked checked against the recorded transient count, total and threshold. Scoring trusts marked for eligibility. This conflicts with DEC-T06-INFRA-INVALID (.genesis/project.json:744). Evidence: run.py (harness/run.py:338), score.py (harness/score.py:397), score.py (harness/score.py:540).
   - Table identity is checked only across runs that reached _score_one. A fourth completed run refused during loading contributes no table hash; three accepted runs can therefore leave identical_tables and eligible_as_baseline true. The active record says all runs of an eligible set have identical tables. Evidence: score.py (harness/score.py:499), score.py (harness/score.py:560), score.py (harness/score.py:570), DEC-T06-MANIFEST-6 (.genesis/project.json:1179).
2. Numeric validation — CONTRADICTS an active record or a SPEC requirement. I checked these instances in memory against the current validate_run; it accepted each altered micro-run:
   - input_tokens and output_tokens accept negative integers. The parent token wrapper also records provider values without a range check, so this does not require rewriting output files. Negative counts can flow into the cost sum, contrary to the token-count cost required by NFR-6 (SPEC.md:47) and DEC-T06-COST-3 (.genesis/project.json:1095). Evidence: run.py (harness/run.py:90), score.py (harness/score.py:344), cost.py (harness/cost.py:131).
   - wall_s accepts negative values, NaN and infinity; queue_s has the same unchecked numeric range. wall_s directly supplies the latency figures, contrary to the wall-clock latency requirement in NFR-6 (SPEC.md:47). Evidence: score.py (harness/score.py:96), score.py (harness/score.py:338).
   - result.log.latency_s explicitly accepts None, although DEC-T06-MANIFEST-6 promises numbers for times. It also accepts negative and non-finite floats. Evidence: score.py (harness/score.py:368), DEC-T06-MANIFEST-6 (.genesis/project.json:1179). None may fail later while computing latency; the promised load-time validation does not catch it.
3. Test claims — IMPROVEMENT only. ORDER_PROBE establishes that items.jsonl was opened before the first hidden-file open, but it does not establish that its hash was compared before that open. The current implementation does compare it first: score.py (harness/score.py:325), test_score.py (tests/t06_harness/test_score.py:812). The report test now accurately limits its evidence-value check to a sample, though its fixed-note assertion remains tied to the implementation’s own NOTES value: test_score.py (tests/t06_harness/test_score.py:341).

I ran only read-only, in-memory validation probes, not the timed gate.
